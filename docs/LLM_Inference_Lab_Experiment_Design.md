# LLM Inference Optimization & Evaluation Lab — Experiment Design

**Project scope:** reproducible single-GPU LLM inference benchmarking and evaluation framework  
**Primary baseline model:** `Qwen/Qwen3.5-4B` (text-only path)  
**Initial hardware:** NVIDIA RTX 4090, 24 GB VRAM  
**Status:** design specification before implementation

## 1. Purpose

This project studies how practical LLM-serving choices affect latency, throughput, memory use, and output quality. The objective is not to build a one-off benchmark script, but a reproducible experiment system in which workload definition, backend execution, measurement, aggregation, and reporting remain cleanly separated.

The final framework should support the claims currently made on the resume:

- Compare Hugging Face Transformers and vLLM across precision, batching, model size, quantization, and context length.
- Measure TTFT, tokens/sec, end-to-end latency, peak VRAM, batch scaling, and context-length scaling.
- Evaluate FP16/BF16 and 4-bit/NF4 configurations for memory savings, performance trade-offs, and output-quality drift.
- Produce repeatable experiment runs and reports that identify serving bottlenecks and support practical model-serving and capacity decisions.

## 2. Research Questions

The project is organized around five questions.

1. **Batch scaling:** How does increasing batch size change aggregate throughput, per-request latency, and VRAM consumption?
2. **Context scaling:** How does input context length affect prefill cost, TTFT, end-to-end latency, and KV-cache / memory pressure?
3. **Backend choice:** Under equivalent workloads, when does vLLM outperform a plain Transformers execution path, and by how much?
4. **Precision and quantization:** What memory savings are obtained from FP16/BF16 to 4-bit/NF4, and what latency / throughput / output-quality trade-offs result?
5. **Capacity planning:** Given a model, hardware target, context distribution, and concurrency/batch level, what configuration offers the best latency-throughput-memory trade-off?

Conceptually, the performance surface is:

`Performance = f(model, backend, dtype, quantization, batch_size, context_length, output_length, workload_shape)`

with observed outputs including latency, throughput, TTFT/TPOT, memory use, failure/OOM boundaries, and later output-quality drift.

## 3. Scope and Experimental Boundaries

### In scope

- Single NVIDIA GPU experiments first.
- Text-only generation, even when the selected model is multimodal.
- Deterministic generation for performance experiments.
- Synthetic controlled workloads first; real evaluation datasets later.
- Raw per-run results plus aggregated summaries.
- Hugging Face Transformers first, then vLLM.
- FP16/BF16 first, then 4-bit/NF4.
- Reproducible configuration files and environment metadata.

### Out of scope for the early versions

- Multi-GPU / tensor parallelism.
- Distributed serving clusters.
- Multimodal image-token benchmarking.
- Speculative decoding, prefix caching, CUDA graphs, custom kernels, or TensorRT-LLM optimization.
- Production SLO enforcement.

These can become future extensions after the core measurement system is trustworthy.

## 4. System Architecture

The experiment system is divided by responsibility:

`Experiment Specification -> Workload Generator -> Backend Runner -> Metric Collector -> Result Store -> Aggregator / Report`

### 4.1 Experiment Specification

Defines the controlled state of one experiment. It answers: **What exactly am I running?**

A single `ExperimentConfig` represents one concrete configuration, not an entire scaling study. For example:

- model: `Qwen/Qwen3.5-4B`
- backend: `transformers`
- dtype: `bfloat16`
- batch size: `4`
- target input tokens: `512`
- max new tokens: `128`
- warm-up runs: `2`
- measured runs: `5`

A batch-scaling or context-scaling study is therefore a collection of ExperimentConfig instances generated by a higher-level experiment plan or matrix.

### 4.2 Workload Generator

Constructs a controlled, reproducible inference workload. It answers: **What input will the model receive?**

The workload generator is broader than ordinary preprocessing. It is analogous to a load generator in systems benchmarking. Its responsibilities are:

- construct deterministic prompts;
- control target token length using the model tokenizer;
- verify actual token lengths;
- create batches with defined workload shape;
- record workload metadata such as seed, workload type, requested and actual token counts.

Backend-independent workload construction remains separate from backend-specific preprocessing. The workload may contain plain prompt strings and metadata; the Transformers backend converts those prompts to tensors, while the vLLM backend later converts the same workload into its own request representation.

### 4.3 Backend Runner

Executes inference for a supplied configuration and workload. It answers: **How is this workload executed by this backend?**

The initial Hugging Face backend owns backend-specific operations such as:

- model / processor loading;
- device and dtype placement;
- backend-specific tokenization or tensor preparation;
- warm-up execution;
- deterministic generation;
- CUDA synchronization around timed regions.

The benchmark orchestration layer should not contain Hugging Face-specific logic. Later, vLLM should be plugged into the same pipeline without changing workload generation, result schemas, or aggregation logic.

### 4.4 Metric Collector

Measures observable execution behavior. It answers: **What happened during this run?**

Initial trustworthy metrics:

- end-to-end generation latency;
- actual generated token count;
- aggregate generated tokens/sec;
- peak GPU memory allocation / peak VRAM metric with a clearly documented definition.

Later measurement versions add TTFT and TPOT once the generation path exposes first-token timing correctly. A metric should not be reported until its timing boundary and units are precisely defined.

### 4.5 Result Store and Aggregator

Raw results are the source of truth. Each measured execution produces one `RunResult`. A collection of RunResults for the same ExperimentConfig is aggregated into an `ExperimentSummary`.

Raw data should be preserved even when summaries are produced. This makes outliers, variance, regression analysis, and later re-aggregation possible.

## 5. Core Data Objects

### ExperimentConfig — “What am I running?”

Contains only the desired experiment state and control parameters. Candidate fields:

- experiment ID / configuration ID;
- model ID and optional model revision;
- backend;
- dtype / precision;
- batch size;
- requested input-token length;
- max new tokens;
- deterministic generation settings;
- warm-up run count;
- measured run count;
- seed.

### Workload — “What am I feeding the backend?”

Represents constructed benchmark input, not the generator behavior itself. Candidate fields:

- workload ID / type;
- prompt list;
- requested token length;
- actual token lengths per request;
- batch size;
- seed;
- optional workload provenance / dataset name in later versions.

### RunResult — “What happened in one measured execution?”

Contains observed facts for one run. Candidate fields:

- experiment ID;
- run ID / timestamp;
- actual input-token count;
- actual output-token count;
- end-to-end latency;
- throughput;
- peak VRAM;
- later: TTFT and TPOT;
- success/failure/OOM status;
- environment metadata such as GPU, CUDA, PyTorch, Transformers/vLLM versions.

For analysis portability, important config fields may be denormalized into the stored result even when the experiment ID is also retained.

### ExperimentSummary — “What do repeated runs say?”

Aggregates N RunResults for a single ExperimentConfig. Candidate statistics:

- number of successful / failed runs;
- mean and median latency;
- p95 latency when sample count is sufficient;
- latency standard deviation;
- mean / median throughput;
- maximum observed peak VRAM;
- later: median TTFT / TPOT and their variability.

## 6. Measurement Methodology

### Controlled variables

For each study, change one primary variable while holding the remaining major factors constant whenever possible.

**Batch-scaling study:** vary batch size; hold model, backend, dtype, context length, output length, generation mode, hardware, and workload construction constant.

**Context-scaling study:** vary target input-token length; hold model, backend, dtype, batch size, output length, generation mode, and hardware constant.

**Precision study:** vary FP16/BF16; hold all other factors constant.

**Backend study:** vary Transformers/vLLM while using the same model weights/revision, workload, generation constraints, dtype, hardware, and comparable batching semantics.

### Timing rules

- Model download time is excluded.
- Model load time is excluded from request latency, but may later be measured separately as startup latency.
- Warm-up runs are excluded from reported steady-state metrics.
- CUDA asynchronous execution requires synchronization at timing boundaries where host-side timers are used.
- Performance runs use deterministic decoding so sampling behavior does not add unnecessary output variance.
- Requested token counts and actual token counts are both recorded.

### Repeatability

Every result should be reproducible from:

`code revision + experiment config + model ID/revision + workload seed/data + software environment + hardware metadata`

## 7. Versioned Experimental Roadmap

### V0.1 — Trustworthy Hugging Face Baseline

**Goal:** build the smallest end-to-end experiment pipeline that produces trustworthy raw performance data with one backend and no quantization.

**Model:** `Qwen/Qwen3.5-4B`, text-only generation.  
**Backend:** Hugging Face Transformers.  
**Precision:** FP16 and BF16.  
**Hardware:** RTX 4090 24 GB.

**System work**

- Implement ExperimentConfig, Workload, RunResult, and ExperimentSummary.
- Implement deterministic synthetic workload generation with verified token lengths.
- Implement the HF backend and clean timing boundaries.
- Separate warm-up and measured runs.
- Persist raw run data and experiment summaries.
- Capture software and hardware metadata.

**Experiments**

1. Smoke baseline: batch=1, context=512, output=128.
2. Batch scaling: batch in {1, 2, 4, 8}, fixed context=512 and output=128.
3. Context scaling: context in {128, 512, 1024, 2048}, fixed batch=1 and output=128.
4. Precision comparison: FP16 vs BF16 on representative batch/context points.

**Metrics**

- end-to-end latency;
- generated tokens/sec;
- peak VRAM;
- success/OOM state;
- run-to-run variability.

**Questions V0.1 should answer**

- Does throughput scale with batch size on the 4090, and where do latency/memory costs begin to dominate?
- How quickly does end-to-end latency rise with context length?
- Does BF16 materially differ from FP16 in speed or VRAM for this model/hardware?
- What are the first practical memory limits of this configuration?

**Exit criterion:** one command/config can reproduce a full experiment and produce raw + summarized results without manual measurement.

### V0.2 — Fine-Grained Latency Decomposition

**Goal:** move from coarse end-to-end timing to serving-relevant latency metrics.

**System work**

- Add a streaming or manually instrumented generation path that exposes the first generated token.
- Define and document timing boundaries for TTFT and TPOT.
- Validate metric definitions against end-to-end timing.
- Add p50/p95 reporting where repetition count supports it.

**Experiments**

- Repeat context scaling while measuring TTFT.
- Repeat output-length scaling to isolate decode behavior.
- Compare TTFT vs TPOT sensitivity to context and output length.

**Metrics added**

- TTFT: request start to first output token;
- TPOT: average time per output token after first token;
- decode tokens/sec;
- optional prefill vs decode decomposition where implementation permits.

**Expected interpretation:** context length should primarily pressure prefill/TTFT, while generated sequence length primarily exposes decode cost. Results should be described empirically rather than assumed.

**Exit criterion:** TTFT/TPOT are measured with documented, defensible timing semantics rather than approximated from a blocking `generate()` call.

### V0.3 — Transformers vs vLLM Backend Comparison

**Goal:** evaluate backend-level serving efficiency with identical model/workload definitions.

**System work**

- Add a vLLM backend implementing the same backend contract.
- Reuse the same Hugging Face cached model artifact when possible.
- Normalize output-token accounting and metric definitions across backends.
- Add backend-specific metadata without contaminating common result schemas.

**Experiments — Stage A: controlled offline comparison**

- HF vs vLLM at batch={1,2,4,8}.
- HF vs vLLM at context={128,512,1024,2048}.
- Representative FP16/BF16 comparisons where both paths support equivalent execution.

**Experiments — Stage B: serving-shaped workload**

- Concurrent request loads rather than only fixed offline batches.
- Variable input/output sequence lengths.
- Increasing concurrency until latency degrades or memory becomes limiting.

**Questions V0.3 should answer**

- Is there a meaningful vLLM advantage at low batch/concurrency?
- At what workload shape does the backend difference become substantial?
- How do throughput gains trade against per-request latency and VRAM?
- Which effects are attributable to serving-oriented scheduling/memory management rather than model quality?

**Exit criterion:** backend conclusions are based on comparable workloads and distinguish simple offline batching from serving-style concurrency.

### V0.4 — 4-bit / NF4 Quantization and Quality Drift

**Goal:** quantify whether lower-precision weights provide useful memory savings without unacceptable performance or output-quality degradation.

**Configurations**

- FP16 baseline;
- BF16 baseline;
- 4-bit NF4 configuration;
- optional AWQ/GPTQ extension after NF4 is stable.

**Performance experiments**

- Peak VRAM reduction relative to FP16/BF16.
- Batch/context headroom gained from quantization.
- E2E latency, TTFT, TPOT, and throughput changes.
- Maximum feasible batch/context combinations before OOM.

**Quality evaluation**

Use a fixed, versioned evaluation set and deterministic settings. The exact datasets can be chosen based on model compatibility, but the framework should separate quality evaluation from the synthetic performance workload. Candidate evaluation types:

- deterministic reasoning / QA tasks;
- code-generation tasks if appropriate;
- exact-match or task accuracy when a canonical answer exists;
- output similarity or model-graded criteria only when deterministic task metrics are unsuitable.

Report absolute quality and drift relative to the FP16/BF16 baseline rather than merely comparing text samples.

**Key derived measures**

`Memory saving = 1 - VRAM_quantized / VRAM_baseline`

`Performance delta = (throughput_quantized - throughput_baseline) / throughput_baseline`

`Quality drift = quality_quantized - quality_baseline`

**Exit criterion:** the project can make an evidence-backed statement such as “4-bit NF4 saves X% peak memory under workload Y, changes throughput by Z%, and causes Q points of measured quality drift on evaluation set E.”

### V0.5 — Model Size and Model-Family Scaling

**Goal:** test whether conclusions remain stable when the model changes.

**Model strategy**

- Prefer model-size comparisons within the same family/version when suitable checkpoints exist.
- Use Qwen and Mistral as the two primary open model families.
- When parameter count, generation, architecture, tokenizer, or model family change together, label the study a representative serving comparison rather than a controlled causal architecture comparison.

**Experiments**

- Compare small vs larger models under fixed hardware and workload definitions.
- Measure latency/throughput/VRAM scaling with parameter count.
- Identify the configurations that become VRAM-limited first.
- Repeat selected backend and quantization comparisons on a second model family.

**Questions V0.5 should answer**

- Which findings generalize across models?
- How does parameter scale reduce batch/context headroom on a 24 GB GPU?
- Does the relative advantage of vLLM or quantization change as model size grows?

**Exit criterion:** the framework supports more than one model without model-specific changes leaking into experiment orchestration.

### V0.6 — Reproducible Reports and Capacity Decisions

**Goal:** convert benchmark measurements into engineering decisions rather than a collection of numbers.

**System work**

- Automated experiment matrix runner.
- Standard raw-results format (JSONL/Parquet) and summary format.
- Versioned report generation.
- Dockerized or otherwise pinned runtime for reproducibility.
- Git commit / model revision / dependency capture.

**Core plots**

- throughput vs batch size;
- latency vs batch size;
- TTFT vs context length;
- peak VRAM vs context length;
- throughput vs peak VRAM;
- precision/quantization trade-off plot;
- backend comparison under concurrency;
- model-size scaling plots.

**Decision outputs**

Each report should end with practical statements such as:

- configuration with best throughput under a given latency ceiling;
- maximum tested batch/context before OOM;
- memory headroom gained by quantization;
- when vLLM becomes worthwhile relative to plain Transformers;
- whether a configuration is latency-, compute-, or memory-constrained based on observed evidence.

**Exit criterion:** a reader can use the report to choose a serving configuration without reading benchmark implementation code.

### V1.0 — Portfolio-Ready Reproducible Benchmark Suite

V1.0 is reached when all four resume claims are supported by committed code, versioned configurations, raw results, plots, and written conclusions.

The final repository should make it possible to:

1. install/pin the environment;
2. select a model/backend/configuration;
3. generate a deterministic workload;
4. run repeated benchmarks;
5. persist raw results;
6. aggregate and plot metrics;
7. run quality evaluation for quantized configurations;
8. reproduce a report from saved experiment artifacts.

## 8. Suggested Experiment Matrix

The matrix should grow incrementally rather than being run in full before the harness is trustworthy.

| Study | Fixed | Variable | Initial values | Primary outputs |
|---|---|---|---|---|
| Smoke baseline | Qwen3.5-4B, HF, BF16 | none | bs=1, ctx=512, out=128 | correctness, E2E, tok/s, VRAM |
| Batch scaling | model/backend/dtype/ctx/out | batch | 1, 2, 4, 8 | tok/s, E2E, VRAM |
| Context scaling | model/backend/dtype/bs/out | context | 128, 512, 1024, 2048 | E2E, later TTFT, VRAM |
| Precision | model/backend/workload | dtype | FP16, BF16 | latency, tok/s, VRAM |
| Decode scaling | model/backend/dtype/bs/ctx | output tokens | 32, 128, 256, 512 | TPOT, E2E, tok/s |
| Backend | model/dtype/workload | backend | HF, vLLM | TTFT, TPOT, throughput, VRAM |
| Quantization | model/backend/workload | precision | FP16/BF16, NF4 | VRAM, speed, quality drift |
| Model scale | hardware/workload methodology | model | feasible Qwen/Mistral sizes | scaling curves, OOM boundary |

## 9. Result Storage Convention

A practical artifact hierarchy:

```text
results/
  raw/
    <experiment_id>.jsonl
  summaries/
    <experiment_id>.json
  manifests/
    <experiment_id>.yaml
reports/
  figures/
  benchmark_report.md
```

Each result should be traceable back to the exact experiment configuration and environment. Raw results are never overwritten merely because a new summary is generated.

## 10. Resume Claim Traceability

| Resume statement | Evidence required from project |
|---|---|
| “Built a reproducible benchmarking framework comparing Hugging Face Transformers and vLLM across precision, batching, model size, quantization, and context-length configurations.” | Config-driven runner; common backend contract; HF/vLLM runs; experiment matrices; multiple model/precision configs |
| “Measured TTFT, tokens/sec, end-to-end latency, peak VRAM, batch scaling, and context-length scaling…” | Metric definitions; raw run files; timing implementation; scaling plots; repeated-run summaries |
| “Evaluated FP16/BF16 and 4-bit/NF4 configurations…” | Quantized configs; memory/performance comparison; fixed quality-eval set; baseline-relative quality drift |
| “Designed repeatable experiment runs and reports to identify serving bottlenecks and guide practical model-serving and capacity decisions.” | Repeated runs; environment capture; versioned reports; OOM/headroom analysis; explicit serving recommendations |

The rule is simple: **a resume claim is considered complete only when the repository contains reproducible evidence for it.**

## 11. Immediate Implementation Order

Before writing a large amount of backend code, implement the architecture in the smallest possible vertical slice:

1. Define `ExperimentConfig`.
2. Define `Workload` and a deterministic `WorkloadGenerator`.
3. Define `RunResult` and `ExperimentSummary`.
4. Implement one Hugging Face backend path.
5. Run one Qwen3.5-4B BF16 smoke benchmark.
6. Persist raw results.
7. Aggregate them into a summary.
8. Only then add batch/context experiment matrices.

This keeps V0.1 focused on a trustworthy measurement pipeline rather than feature count.

## 12. Design Principles

- **Separate experiment intent from execution details.**
- **Keep workload construction backend-independent.**
- **Treat raw measurements as the source of truth.**
- **Do not report a metric before its definition is defensible.**
- **Change one primary experimental variable at a time when making causal comparisons.**
- **Record requested and actual workload sizes.**
- **Prefer small, complete vertical slices over broad unfinished abstractions.**
- **Do not over-engineer future backends before a real second implementation creates a need for abstraction.**
- **Make every resume claim traceable to code, raw evidence, plots, and a written conclusion.**
